# 마법 제작 편의성 비교 테스트

## 1. 목적과 확정된 조건

- 대상: 이전 버전을 어느 정도 플레이해 본 참가자.
- 비교 대상: 현재 Legacy 버전과 편의성을 개선한 Develop 버전.
- 과제: 각 버전에서 편집·도크 시간 5분 동안 가능한 많은 마법을 제작한다. Legacy 구현을 기준으로 Develop 버전과 비교한다.
- 두 버전의 시작 화면에서 `테스트 모드 시작`을 선택하고 참가자 이름 또는 식별값을 입력한다. Develop 테스트 모드에서도 이 진입·입력 흐름을 제공할 예정이다.
- 테스트 모드의 RAM 용량은 기본 용량과 적용된 강화 트리의 RAM 효과를 합산한다. 현재 데이터 기준 6 + 5 + 5 = 16이다.
- 테스트 모드에서는 모든 Modifier 종류를 B등급으로 종류당 2개씩 제공하고, Modifier 이외의 플레이어용 노드는 아래 제외 대상을 뺀 나머지를 제공한다.
- 테스트 제공 제외 대상: 지연(`flow.delay`), 조건(`flow.if`), 마법 메소드(`spell.call`), 회복(`element.healing`), 보호(`element.protection`), 적용(`behavior.apply`). 일반 팔레트·빠른 검색·속성 선택에 같은 제외 기준을 적용하며 일반·디버그 모드에는 적용하지 않는다.
- 테스트 시작 시 강화 트리는 전격까지의 일반 노드를 MAX로 적용한다. 무한 강화 노드(`.endgame`)는 적용하지 않는다. 원본 트리 자산과 일반 저장은 변경하지 않는다.
- 플레이어는 제작한 마법으로 고정된 단일 테스트 스테이지에 출격할 수 있다. 임시로 9스테이지를 사용한다.
- 마법은 해당 설계로 테스트 스테이지를 클리어했을 때 완성으로 인정한다.
- GameAnalytics를 사용하지 않고 로컬 파일에 로그를 기록한다.
- 기대 효과: 같은 시간에 완성하는 마법 수와 종류가 늘고, 제작에 필요한 조작 부담과 실패가 줄어든다.
- 전체 클릭 수의 감소만으로 개선 여부를 판정하지 않는다. 제작량이 늘면 전체 클릭 수도 늘 수 있다.

위 항목 중 Legacy의 테스트 조건은 사용자 요구사항이다. Develop의 이름 입력·단일 고정 스테이지도 비교 테스트 조건에 포함하며, 정확한 스테이지 ID와 입력값의 로그 매핑은 11절에서 확정한다. Legacy 구현 내용과 검증 상태는 13절에 기록한다.

## 2. 테스트 진행 조건

| 항목 | 권장 조건 |
| --- | --- |
| 진입 | 각 버전의 시작 화면에서 `테스트 모드 시작`을 선택하고 동일한 방식으로 참가자 이름 또는 식별값을 입력한다. |
| 제한 시간 | 편집·도크 300초. 전투·결과 화면에서는 타이머를 멈춘다. 종료 후 새 출격은 차단하고 진행 중 전투의 클리어는 인정한다. |
| Legacy 시작 상태 | 전격까지 일반 트리 MAX, 무한 강화 제외. RAM은 트리 효과 합산(현재 16), 모든 Modifier 종류의 B등급 2개씩, 지정한 여섯 종류를 제외한 나머지 플레이어용 노드 제공. |
| Develop 시작 상태 | 참전격까지 일반 트리 MAX, 무한 강화 제외. RAM은 트리 효과 합산(현재 16), 모든 Modifier 종류의 B등급 2개씩, 지정한 여섯 종류를 제외한 나머지 플레이어용 노드 제공. |
| 시작 그래프 | 두 버전에서 같은 설계를 권장한다. 사용할 시작 그래프는 구현 전에 확정한다. |
| 사용 환경 | 가능한 한 동일한 장치, 해상도, 입력 장치, 실행 환경을 사용한다. |
| 안내 | 두 버전에 같은 과제 설명을 제공한다. Develop의 바뀐 조작은 측정 전에 안내한다. |
| 연습 | 안내·연습 시간과 내용을 기록한다. 연습 중 만든 그래프는 측정 시작 전에 초기화한다. |
| 비교 순서 | 가능하면 기존→개선과 개선→기존 순서를 참가자별로 나눈다. 참가자의 기존 플레이 경험도 기록한다. |
| 상태 복구 | 버전이 바뀔 때 이전 테스트의 구매·해금·그래프 변경을 이어받지 않고 시작 조건으로 복구한다. |
| 시간 구분 | 작업실의 편집·구상·도움말·도크는 편집 타이머에 포함한다. 전투·결과 화면과 운영상 중단은 제외한다. 전체 경과 시간은 별도로 남긴다. |
| 중단 | 운영상 중단은 타이머와 측정을 함께 멈추고 사유를 기록한다. 게임 내 도움말·팝업 사용은 중단으로 보지 않는다. |
| 종료 | 편집 300초에 종료하고 현재 그래프를 저장한다. 이후 편집·새 출격을 차단한다. 시작 화면으로 돌아가 새 회차를 시작할 수 있다. |
| 성장·보상 | 테스트에서는 강화 구매와 재화·Modifier·스테이지 진행 보상 반영을 차단해 시작 조건을 유지한다. |
| 테스트 스테이지 | 두 버전 모두 단일 고정 스테이지를 사용한다. Legacy 기준은 임시 9스테이지이며, Develop도 같은 ID를 사용할지 측정 전에 확정한다. 일반 진행의 해금 여부로 테스트 출격이 막히지 않아야 한다. |

모든 참가자가 기존→Develop 순서로 진행한다면, Develop 결과에는 두 번째 테스트의 학습·아이디어 재사용 효과도 포함될 수 있음을 보고서에 명시한다.

참가자에게 제공할 과제 설명 예시:

> 주어진 시간 동안 서로 다른 마법을 가능한 많이 만들어 주세요. 제작한 마법으로 테스트 스테이지에 도전할 수 있습니다. 해당 마법으로 테스트 스테이지를 클리어하면 완성으로 인정됩니다. 완성한 마법을 수정해서 다른 마법을 만들어도 됩니다.

## 3. 완성과 마법 종류의 판정

### 완성 기준

제작한 마법으로 테스트 스테이지(임시 9스테이지)를 클리어하면 완성으로 기록한다. 시험 도크 시전이나 참가자의 완성 표시는 완성 조건으로 사용하지 않는다.

- 출격 시 그래프 스냅샷을 저장하고 `combat_id`와 `spell_build_id`를 연결한다.
- 클리어 시 전투에 실제로 사용한 출격 스냅샷을 완성 기록으로 확정한다. 클리어 뒤 편집 중인 다른 그래프를 대신 사용하지 않는다.
- 실패·후퇴·시간 초과는 전투 시도로 기록하고 완성 수를 증가시키지 않는다.
- 그래프를 변경했다면 변경된 설계로 테스트 스테이지를 다시 클리어해야 한다.
- 같은 설계를 반복 클리어하면 전투 기록은 남기되 고유 완성 수를 중복 증가시키지 않는다.
- 도크 시전 요청·성공 로그는 제작 과정을 해석하는 보조 자료로 유지한다.
- 현재 프로젝트는 하나의 설계를 계속 수정하므로 출격·완성·측정 종료 시의 원본 그래프를 보관한다.

### 종류와 변형 구분

| 변경 | 집계 기준 |
| --- | --- |
| 이름, 노드 위치, 화면 확대·이동, 노드·엣지 ID만 변경 | 같은 설계 |
| 실행에 영향을 주는 형태·행동·속성·흐름·Trigger·Modifier 종류나 연결 구조 변경 | 다른 종류의 마법 |
| 배율, 반복 횟수, 시간, Modifier 등급 등 값만 변경 | 같은 종류의 파라미터 변형 |
| 실행에 영향을 주지 않는 고립 노드만 변경 | 같은 종류. 편집 활동에는 기록 |

완성한 고유 설계 수는 종류와 파라미터 변형을 포함하되 동일 설계 중복을 제외한다. 서로 다른 마법 종류 수는 파라미터 변형을 합쳐 집계한다. 두 값을 따로 보고한다.

구조 비교 키에는 실행 의미와 연결 순서를 보존하고, 표시 이름·좌표·임의 ID를 제외한다. Legacy와 Develop의 편집 구조가 다르므로 버전별 원본 그래프나 원시 서명만으로 마법 종류를 교차 비교하지 않는다. 기존 컴파일 서명이 정규화된 실행 의미를 비교하는지 구현 전에 확인하고, 완성된 원본 그래프는 비교 키와 별도로 보관한다.

## 4. 로그 공통 필드

| 필드 | 의미 |
| --- | --- |
| `participant_id` | 참가자를 구분하는 익명 ID |
| `schema_version` | 로그 형식 버전. 게임 버전과 별도로 관리 |
| `test_session_id` | 참가자 한 명의 한 버전 측정 회차 |
| `app_version`, `condition` | 실행 버전과 Legacy/Develop 조건. 마법 빌드 ID와 구분 |
| `editor_model` | 편집 구조 구분. Legacy의 `line_connected_nodes`와 Develop의 `combined_nodes`를 구분 |
| `test_order` | 해당 참가자가 수행한 버전 순서 |
| `event_name`, `event_seq` | 이벤트 종류와 회차 안의 순번 |
| `timestamp_utc`, `elapsed_ms` | 이벤트 시각은 UTC ISO 8601(`Z`)로 기록. 경과 시간은 기존 단조 증가 시간 기준을 유지 |
| `editing_episode_id` | 편집 구간 ID. 하나의 편집 구간에서 여러 마법을 완성할 수 있음 |
| `graph_revision_id` | 그래프가 바뀔 때 갱신하는 상태 ID. 도크·출격·클리어에 사용한 상태를 연결 |
| `spell_build_id` | 완성·출격 시 보관한 그래프 스냅샷 ID |
| `combat_id` | 전투를 진행하는 경우 한 판의 ID |
| `context` | 편집, 시험 도크, 도움말, 전투, 결과 등 현재 맥락 |
| `is_test_mode`, `is_debug`, `is_practice` | 테스트 모드·디버그·연습 구분. 테스트 모드와 디버그 모드를 같은 기능으로 취급하지 않음 |

회차 시작에는 기존 플레이 경험, 장치·해상도, 안내·연습 시간, 시작 그래프, 능력치, 해금·보유량을 기록한다. 완성·출격·종료 스냅샷에는 그래프 구조·파라미터, 노드·연결 수, RAM 사용량, 컴파일 결과와 관련 진행 능력치를 기록한다.

## 5. 마법 제작 로그

| 이벤트 | 발생 시점 | 주요 기록 |
| --- | --- | --- |
| `test_start` / `test_end` | 측정 시작·종료 | 조건, 시작 상태, 실제 측정 시간, 종료 이유, 마지막 그래프 |
| `editor_enter` / `editor_exit` | 편집 화면 진입·이탈 | 구간 ID, 경과 시간, 이탈 이유 |
| `editor_click` | 편집 중 포인터 버튼 누름 | 버튼 종류, UI 영역, 대상 노드·룬·포트·슬롯, 현재 그래프 상태, 이전 클릭 이후 시간 |
| `editor_action_result` | 의도한 작업 처리 완료 | 편집 모델별 의미 작업(예: Legacy `connect_edge`, Develop `combine_nodes`/슬롯 편집), 입력 경로, 성공·거부·취소, 실패 이유, 연관 클릭 또는 입력 ID |
| `compile_result` | 컴파일 결과 변경 | 유효 여부, 오류·경고 코드, RAM, 노드·연결 수 |
| `simulation_request` | 시험 실행 요청 | 버튼·직접 클릭·단축키·자동 시전 등 요청 경로, 그래프 상태 |
| `simulation_cast_result` | 시험 시전 처리 | 실제 시전 성공 여부, 거부 이유, 시험한 그래프 상태 |
| `spell_complete` | 제작한 마법으로 테스트 스테이지 클리어 | 전투 ID, 출격 스냅샷 ID, 종류·변형 비교 키, 해당 설계의 최초 완성 여부 |
| `stage_enter` | 테스트 스테이지 진입 | 전투 ID, 실제 스테이지 번호(임시 9), 출격 그래프 스냅샷, 능력치 |
| `measurement_pause` / `measurement_resume` | 운영상 측정 중단·재개 | 중단 사유, 제외 시간 |

### 클릭과 작업 결과의 측정 기준

- Legacy는 개별 노드를 선(엣지)으로 연결하고, Develop은 노드를 합치는 편집 모델이다. `editor_model`과 의미 작업 종류를 기록해 두 조작 흐름을 구분한다.
- 두 모델의 원시 노드 수·엣지 수·클릭 수는 표현 방식 차이에 영향을 받으므로 단독으로 직접 비교하지 않는다. 원본 수치는 모델별로 보존하고, 교차 버전 비교는 동일한 마법 의미나 사전에 정의한 정규화 기준을 사용한다.

- 전체 클릭은 편집 과제 중 포인터 버튼을 누른 횟수다. 좌·우·중간 버튼과 영역별 합계를 분리한다. 휠·키 입력은 별도 조작으로 기록한다.
- 드래그는 누름을 클릭 한 번으로 세고, 드래그 완료를 작업 결과 한 번으로 기록한다. 이동 프레임마다 클릭을 만들지 않는다.
- 성공 클릭은 연결된 클릭 기반 작업이 의도대로 처리된 경우다. 실패 클릭은 해당 작업이 명시적인 이유로 거부된 경우다.
- 선택 해제·화면 이동·도움말 열기 등 정상 행동을 실패로 보지 않는다. 구상 중 빈 공간 클릭이나 의도가 불명확한 클릭은 중립·미분류로 남긴다.
- 성공·실패 클릭과 별도로 작업 성공·거부 횟수를 기록한다. 여러 입력으로 수행하는 연결 작업을 클릭 하나와 동일하게 취급하지 않는다.
- 실패 이유는 연결 불가, RAM 초과, 미해금, Modifier 보유량 부족, 편집 잠금 등으로 구분한다.
- 노드별 클릭은 개별 노드 ID와 룬 종류별로 집계한다. 선택·포트 연결·파라미터 조작을 구분한다.
- 클릭 사이 시간은 직전·현재 행동 및 맥락과 함께 기록한다. 긴 간격만으로 불편함을 판정하지 않는다.
- 시뮬레이션 실행 클릭 수, 전체 요청 수, 실제 시전 성공 수를 구분한다. 자동 시전 횟수는 클릭 수에 더하지 않는다.

### 시간과 추가 조작

- 전체 경과 시간, 운영상 중단 시간, 편집 화면 체류 시간, 시험 도크·도움말·테스트 전투 시간을 별도로 기록한다.
- 300초는 작업실 편집·도크 시간이며 전투·결과 화면은 제외한다. 운영상 중단은 작업실에서 F9로 중단·재개한다.
- 실제 편집 시간은 입력 간격만으로 자동 판정하기 어렵다. 유휴 기준을 쓰면 기준을 명시하고 원본 행동 시각을 함께 보관한다.
- 삭제, 실행 취소·다시 실행, 복사·붙여넣기, 연결 재시도, 도움말 사용을 작업 종류로 기록한다.
- 완성 시각의 차이는 완성 간 간격이다. 이전 설계를 재사용하거나 여러 아이디어를 함께 편집했을 수 있으므로 독립 마법의 순수 제작 시간으로 단정하지 않는다.

## 6. 전투 로그

테스트 스테이지 전투는 마법 완성을 판정하는 필수 과정이다. 편집과 전투를 같은 테스트 회차에 연결하고, 전투 시간은 편집 제한시간에서 제외한다.

| 이벤트·항목 | 기록 기준 |
| --- | --- |
| `combat_start` | 전투 ID, 스테이지, 출격 빌드 ID, 능력치, 난수 시드 |
| 전투 시간 | 시작·종료 시각과 일시정지를 제외한 시뮬레이션 진행 시간 |
| `combat_end` | 클리어·사망·후퇴·시간 초과·테스트 종료·앱 종료 등 종료 이유. 시작만 있고 종료가 없는 판은 별도 표시 |
| 받은 피해 | 실제 HP 감소와 보호막 흡수량을 구분. 실제 HP 감소는 사망 시 남은 HP를 넘는 피해를 제외 |
| 입힌 피해 | 실제 적 HP 감소를 기본값으로 사용. 가능하면 직접·상태 이상·잔류 피해를 구분 |

| 공격 유지 시간 | 실제 공격 입력이 전달된 시간. 좌클릭 유지 공격이므로 누름 횟수만으로 공격량을 해석하지 않음 |
| 시전·자원 | 실제 루트 시전 횟수, 에너지 소비, 자원 부족으로 실행 경로가 중단된 횟수 |
| 결과 보상 | 처치 수, 획득·정산 재화, 획득 Modifier |

| 우선순위 | 지표 | 계산·해석 |
| --- | --- | --- |
| 주 지표 | 완성한 고유 설계 수 / 제한시간 | 테스트 스테이지를 클리어한 종류·파라미터 변형의 고유 수 |
| 주 지표 | 서로 다른 마법 종류 수 / 제한시간 | 테스트 스테이지를 클리어한 설계 중 이름·배치·값만 다른 변형을 합친 종류 수 |

| 주 지표 | 작업 실패율 | 거부된 작업 수 ÷ 성공·거부가 판정된 작업 수. 중립·취소는 별도 집계 |

| 보조 지표 | 성공·실패·중립 클릭 수 | 전체 및 UI 영역·조작 종류별 비교 |

| 보조 지표 | 시험 요청·성공 수 | 제작 결과 확인과 실험 활동을 해석 |
| 보조 지표 | 제작 복잡도 | 완성 스냅샷의 모델별 노드·연결 수, RAM, 사용 룬 종류. 노드·연결 수는 편집 모델 간 직접 비교하지 않음 |

- 완성 수가 0이면 완성당 클릭 수는 계산 불가로 표시한다. 0으로 기록하거나 참가자를 분석에서 제외하지 않는다.
- 참가자별 기존·개선 차이를 먼저 계산하고 전체의 중앙값과 분포를 함께 본다.
- 제작량 증가, 종류 증가, 실패·재시도 감소, 체감 편의성을 함께 평가한다.
- 단순 설계만 많이 만든 경우를 확인하기 위해 다양성과 복잡도를 함께 보고한다.
- 편집 화면 체류 시간이나 클릭 간격을 순수 제작 시간·생각 시간으로 단정하지 않는다.
- 완성까지 걸린 시간에는 전투 성과가 영향을 준다. 편집 시간, 출격 전 유효 설계 수, 전투 시도 수를 함께 보고한다.
- 제작량은 편집·도크 300초 기준으로 비교한다. 전투를 포함한 전체 경과 시간도 함께 보고한다.

## 8. 종료 후 설문

각 버전 직후 같은 문항을 1점(전혀 그렇지 않다)~5점(매우 그렇다)으로 묻는다.

1. 원하는 마법을 만들기 쉬웠다.
2. 노드를 배치하고 연결하기 편했다.
3. 만든 마법을 수정하고 다른 마법을 시도하기 편했다.
4. 조작 중 막히거나 의도와 다르게 처리되는 순간이 적었다.

두 버전을 모두 수행한 뒤 어떤 버전이 더 편했는지, 구체적으로 어떤 조작이 좋아졌거나 어려웠는지 자유 응답을 받는다.

## 9. 구현·기록 연결 시 확인할 사항

- GameAnalytics SDK·연동·외부 전송을 추가하지 않는다. 원본 이벤트·그래프·요약을 로컬 파일로 보관한다.
- 시작 화면의 테스트 모드 진입은 일반 시작·디버그 시작과 구분한다. 테스트 상태와 지급 규칙을 별도로 적용한다.
- 테스트에서도 일반 능력치 계산 경로로 기본 RAM과 트리 효과를 한 번만 합산한다. 이전의 RAM 10 고정 처리는 사용하지 않는다.
- 플레이어용 노드 제공은 지정 제외 대상을 뺀 해금·팔레트 제공 범위를 의미한다. 중복 Core나 내부 전용 노드를 임의로 배치 가능하게 바꾸지 않는다.
- Modifier B등급의 실제 지원 여부를 기존 등급표에서 확인한다. 없는 등급을 다른 등급으로 조용히 대체하지 않는다.
- 일반 플레이 저장을 테스트 진행으로 덮어쓰지 않는 독립 상태를 권장한다. 기존 디버그 모드의 지급량·무적 규칙을 그대로 재사용하지 않는다.
- 기존 LocalTelemetry는 로컬 디버깅 기록이다. 현재 버퍼만으로 테스트 전체 원본 기록을 보존할 수 있는지 확인한다.
- 이벤트 발생 위치는 편집 입력·명령 처리 결과, 도크 요청·실제 시전, 출격 스냅샷, 미션 시작·종료·클리어 확정, 세션 보상 반영으로 나눈다.
- UI 갱신이나 매 프레임 처리에서 같은 사용자 행동을 중복 기록하지 않는다.
- 테스트 종료는 게임 종료와 구분한다. 확정된 타이머 정책의 집계 마감 이후 조작은 본 측정 집계에 더하지 않는다.
- CLI·디버그·연습 기록은 본 측정과 분리한다.
- 참가자가 아무 마법도 완성하지 못하거나 종료 이벤트가 누락된 경우도 보존한다.
- 실제 수집 검증 시 테스트 진입·지급량, 9스테이지 진입, 클릭 중복, 드래그, 단축키, 도크 요청 거부, 운영상 중단, 제한시간 종료, 클리어 기반 완성·중복 판정, 파일 저장을 확인한다.

## 10. 로컬 로그 저장 형식 권장안

원본은 JSONL, 그래프·회차 정보는 JSON, 비교표는 CSV로 저장한다. JSONL은 한 줄에 JSON 객체 하나를 기록하는 형식이며 일반 JSON 배열 파일과는 구분한다.

| 파일 | 용도 |
| --- | --- |
| `session.json` | 형식·게임 버전, 참가자·회차 ID, Legacy/Develop 조건과 `editor_model`, 테스트 순서, 시작 조건, 타이머 정책, 진행·종료 상태 |
| `events.jsonl` | 시간순 원본 클릭·작업·도크·전투·완성 이벤트. 매 이벤트에 공통 필드와 해당 이벤트의 `data` 객체를 기록 |
| `builds/{spell_build_id}.json` | 출격·완성·종료 그래프 원본, 비교 키, 컴파일 결과, 능력치. 스냅샷 ID로 이벤트와 연결 |
| `summary.csv` | 회차별 한 행의 집계. 클릭·실패·도크·완성·종류·시간 지표. 여러 회차를 합쳐 비교 가능 |
| `combats.csv` | 전투별 한 행의 집계. 빌드 ID, 결과, 시간, 피해, 대시·공격·클릭 지표 |

저장 위치는 `Application.persistentDataPath/UsabilityTests/{test_session_id}/`를 권장한다. Legacy와 개선 버전의 파일 이름이 충돌하지 않도록 회차 ID를 사용하고, 참가자·실행 버전은 `session.json`에도 명시한다. 결과 폴더 전체를 복사하면 분석에 필요한 원본을 함께 전달할 수 있어야 한다.

### 이벤트 구조 예시

다음 값은 형식 설명용 가상 예시다.

```json
{"schema_version":4,"participant_id":"P001","test_session_id":"session-example","app_version":"legacy-test-01","condition":"Legacy","editor_model":"line_connected_nodes","event_name":"editor_action_result","event_seq":12,"timestamp_utc":"2026-10-15T00:00:02.400Z","timezone":"UTC","elapsed_ms":2400,"context":"editor","is_test_mode":true,"data":{"editing_episode_id":"edit-01","graph_revision_id":"graph-03","action":"connect_edge","input_method":"drag","result":"rejected","reason":"invalid_connection","input_id":"input-08"}}
```

현재 로그 writer는 `schema_version` 4를 사용한다. 의미가 같은 B 형식 필드는 B 이름으로 기록한다: 요약의 `duration_ms`는 초 단위 `elapsed_seconds`, `editor_click_count`는 `editor_clicks`, 성공·거절 행동 수는 `successful_actions`·`failed_actions`로 출력한다. 전투 시간은 `duration_ms`에서 `seconds`로 변환하고, `damage_received`·`dash_inputs`·`dashes_started`는 `damage_taken`·`space_presses`·`dash_count`로 기록한다. 컴파일 결과는 `ok`·`ram`·`nodes`·`edges`, 전투 종료 이벤트는 `kills`, 빌드 스냅샷은 `compile_ok`를 사용한다. 의미나 기록 범위가 일치한다고 확정할 수 없는 시전·요청 카운트와 그래프 서명은 별칭 처리하지 않으며, 기존 로그 파일도 변경하지 않는다.

- 원본 이벤트를 유일한 집계 근거로 사용한다. 완성 기록에는 클리어한 전투와 출격 스냅샷을 연결하고, 반복 클리어는 원본에 남기되 집계에서 중복을 제외한다.
- 클릭마다 전체 그래프를 복제하지 않는다. 그래프 원본은 필요한 스냅샷에 저장하고 이벤트는 ID로 참조한다.
- 이벤트 순서와 원본을 기준으로 요약을 다시 계산할 수 있게 한다. 집계 CSV만 남기지 않는다.
- UTF-8로 저장한다. JSON 숫자는 문화권과 무관하게 직렬화하고, CSV는 쉼표·따옴표·줄바꿈이 포함된 값을 올바르게 감싼다.
- 값이 없거나 계산 불가인 항목은 JSON `null`, CSV 빈 칸으로 표현한다. 0과 구분한다.
- JSONL은 순차 추가 기록하고 정해진 짧은 간격과 출격·클리어·테스트 종료 시 flush한다. 매 클릭마다 동기 파일 쓰기를 하지 않는다.
- `session.json`은 임시 파일을 거쳐 교체하는 방식을 권장한다. 이벤트 마지막 줄이 비정상 종료로 잘렸다면 완전한 앞선 줄은 읽을 수 있어야 한다.
- 저장 실패를 숨기지 않고 사용자에게 표시한다. 종료 기록이 없으면 분석에서 비정상 종료·불완전 회차로 구분한다.
- 원본·요약·CSV를 같은 형식 버전과 이벤트 정의로 맞추고, 외부 AI 분석 시 이 문서를 함께 전달한다.

## 11. 구현 전에 확정할 사항

1. Develop 편집 모델의 정확한 의미 작업·지급 조건. 이번 변경 작업은 Legacy 로그와 비교 기준 정리에 초점을 둔다.
2. Develop의 고정 테스트 스테이지 ID가 Legacy의 9스테이지와 동일한지 확인한다. 참가자 이름 입력값을 익명 `participant_id`로 사용할지 별칭으로 변환할지도 확정한다.
3. `editor_model`을 필수 로그 필드로 추가할 때 `schema_version`을 2에서 3으로 올리고, 집계 도구가 기존 1·2 형식 로그를 계속 읽도록 한다.

## 온라인 로그 전송 (2026-10-16)

목표는 참가자가 파일을 수동으로 보내지 않아도 완료된 테스트 로그를 연구자 PC에 수집하는 것이다. 원본 JSONL 기록 방식은 유지한다. 무료 Cloudflare Workers 고정 주소에 ZIP을 전송하고 D1에 임시 보관한다. PC의 분석 도구가 실행 중이면 30초마다 내려받아 기존 정리 파이프라인 및 분석 화면으로 연결한다. PC가 꺼져 있어도 온라인 수신은 유지된다. 서버·분석 도구·실제 전송 키는 프로젝트에 포함하지 않는다.

`RuneCodeApp`이 `UsabilityLogUploader`를 연결한다. `StreamingAssets/LogUploadSettings.json`의 `_isEnabled`, `_endpoint`, `_uploadToken`으로 활성화한다. 저장소 기본 설정은 비활성화되어 있다. `LogUploadBuildProcessor`가 Windows 빌드 후 바탕화면 `PlayLogWorkbench/GameConfig/LogUploadSettings.json`을 결과물의 `*_Data/StreamingAssets`에 자동 포함한다. 수집기를 먼저 실행한 뒤 평소처럼 빌드하면 되며 Inspector 연결과 수동 파일 복사는 필요 없다. 설정 파일이 없는 PC에서는 경고하고 기본 설정을 유지한다. 잘못된 설정이나 복사 실패는 빌드 오류로 보고한다. 프로젝트의 원본 설정 및 실제 전송 키는 변경하지 않는다. 이미 배포한 게임은 주소가 바뀌면 설정 파일 교체가 필요하다.

완료된 세션은 15초 주기로 최신순 전송한다. 종료 요청에서는 세션을 먼저 마감하고 최대 6초 전송을 시도한다. 성공한 세션에만 `upload.receipt`를 남기고 실패한 원본은 다음 실행에 재시도한다. 강제 종료·장애 중 즉시 전달은 보장하지 않는다. 대상 파일은 events.jsonl, session.json, summary.csv, combats.csv 및 builds/*.json이며 압축 32MB·원본 합계 64MB로 제한한다.

완료 기준은 인증된 세션의 온라인 보관·PC 저장 및 자동 정리, 동일 로그 중복 방지, 실패 시 원본 보존과 재시도, 새 로그의 그래프 반영이다. 최초 한 번 `SetupCloudCollection.cmd`로 Cloudflare 무료 계정을 연결한다. 주소는 수집기를 재시작해도 유지되며 Windows 빌드에는 최신 설정을 자동 포함한다. 이전 임시 터널 주소는 새 빌드에서 거부한다. 이미 임시 주소로 배포한 게임은 최초 한 번 고정 설정이 포함된 빌드로 교체해야 한다.

온라인 보관은 무료 단일 D1 데이터베이스 한도보다 작은 384MiB로 제한한다. 한도 도달 시 새 전송을 거부하고 참가자 PC 원본을 유지한다. PC 전용 수신 키는 게임 전송 키와 분리한다. 다운로드 크기와 SHA-256, ZIP 경로 및 로그 형식을 검사하고 PC 원본·정리본 저장이 끝난 뒤에만 온라인 ZIP을 정리한다. 재전송 중복 방지를 위한 해시 수신 기록은 유지하며 Cloudflare 자체 복구 보관 정책은 별도로 적용된다. 수집함을 조회하거나 삭제하는 관리자 키는 게임에 포함하지 않는다. 유료 요금제 전환이나 결제 수단 등록은 자동 수행하지 않는다.
